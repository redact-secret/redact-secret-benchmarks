# Run the four required scanners by default and make the optional OpenRedaction default profile a positive opt-in

## Context

The owner decided (#763, 2026-10-06) that the OpenRedaction default (all-pattern) profile is an optional, manual measurement. That decision made it optional in the evaluation contract (`benchmarks/support/scanner-roster.json`) and gave the official run a way to leave it out (`omit_optional`, driver `--omit-optional`). It did not change what a normal run does: `omit_optional` defaulted to an empty string, so a Full dispatch still selected the registry's five-scanner configuration and ran the expensive profile unless the dispatcher remembered the switch (#812). The pinned engine (credential-eval v0.1.0-alpha.15, and every release since v0.1.0-alpha.13) already ships `configs/official/credential-public-v1.without-openredaction.json` and its darwin-arm64 variant, so no engine release is needed.

## Decision

1. **One effective scanner-selection policy.** `benchmarks/qualification/scanner-selection.ts` is the single place that turns the roster and the registry into what a run executes. The workflow, the driver, the execution plan, the replay scripts and provisioning all go through it (or its plain-Node twin `scripts/official-run-selection.mjs` for scripts that cannot import TypeScript). With no input a Full run measures `flare-redact`, `gitleaks`, `redact-secret` and `trufflehog` under the engine's released without-OpenRedaction configuration. OpenRedaction scan invocations: zero.
2. **OpenRedaction is a positive opt-in.** Workflow input `include_openredaction` (default `false`), driver `--include-optional openredaction`, replay scripts `--include-openredaction`, planner `--include-openredaction`. The opt-in selects the engine's full configuration. It is shown in the plan, the dispatch command, the run name, the job summary and the run record (`scannerSelection`: configuration file and hash, scanners, `includedOptionalScanners`). The registry check binds a recorded selection to the scanners the run measured. The credential profile (`openredaction-credential-bearing`) is in no official configuration and cannot be included here (#764).
3. **`omit_optional` is deprecated, not removed.** It still works (a caller that passes it, such as an in-flight replay dispatching from a branch that carries its own copy of the workflow, keeps working) and now changes nothing: omitting is the default. The driver and the plan job print a deprecation notice. It contradicts `include_openredaction` and is refused with it.
4. **Availability comes from the pinned engine, not from a claim.** The driver asks the pinned engine's checkout whether the without-config exists. A pinned engine without it is refused plainly. The default never falls back to the full configuration, because that would run the expensive scanner by accident. The full configuration stays selectable only by the explicit opt-in, which keeps the historical five-scanner measurement reproducible. The roster's `engineRelease` records the first release that ships the configurations (v0.1.0-alpha.13, verified against the release tree) and is informational; no run decision reads it.
5. **A retry or a missing artifact never changes the selection.** `retry_run_id` reuses a stage receipt only when its scanner set, its configuration file and its opted-in optional scanners are exactly this run's (`receipt-reuse.ts`); anything else is rejected with the reason and the stage measures fresh under the current selection. The driver also refuses an artifact whose scanner set differs from the selection. The view-only reuse inputs, `populations` rehearsals and the diagnostic lane refuse `include_openredaction` (nothing is scanned there, or the lane picks its own scanners).
6. **Candidate and attribution runs match their control, or are reported incompatible.** A candidate replay is compared with the control of its adoption record, whose scanner set is read from its recorded runs. The driver, `run-candidate-replay.mjs dispatch` (before any CI minute is spent) and `collect` refuse a different roster and say how to create the matching control explicitly (`run-evidence-replay.mjs dispatch --include-openredaction`, or the default). The control replay records the roster it measured (`replay.scannerSelection`), is refused when its run records disagree with the selection it was asked for, and a run dispatched for another selection is never reused (the run name carries the opt-in). Observations are never spliced across rosters. An attribution run uses the engine's own attribution configuration, and the engine ships no without-OpenRedaction variant of it: the default attribution run needs `attributionRuns[<id>].withoutConfigs` in the registry and is otherwise refused with that instruction; the full-roster attribution run is the explicit opt-in.
7. **Provisioning is filtered to the selection.** `provision-official-peers.mjs` downloads an optional scanner's executable only on the opt-in. OpenRedaction is an npm package that the engine lockfile installs with `npm ci --ignore-scripts`; that install cannot be filtered and runs no scan.
8. **Missing optional results stay explicit.** The view and the reports state `OpenRedaction default: not measured in this run (optional)` with the pointer to the last measurement, as before; prior OpenRedaction history, the reviewed qualification contracts, thresholds, support verdicts and `benchmarks/qualification-authority.json` are untouched.

## Consequences

- A normal Full dispatch no longer spends about 50 minutes of OpenRedaction scanner time on the public population, and its job summary and dry run say that OpenRedaction was omitted and show zero invocations.
- The control replay and candidate replays default to the same four-scanner roster. A control recorded earlier with five scanners is incompatible with a default candidate replay; the tooling reports it and names the two ways out. Nothing is silently matched.
- No new credential-eval release, no repin, no change to #764's paused measurement (#725 stays closed).
