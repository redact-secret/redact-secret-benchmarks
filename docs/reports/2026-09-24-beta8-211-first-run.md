# Beta.8 developer credential arrival evidence: first run (#211)

Issue [#211](https://github.com/redact-secret/redact-secret-benchmarks/issues/211)
adds arrival evidence for four developer credential families that no registry
detector targets. Research inputs are
[#222](https://github.com/redact-secret/redact-secret-benchmarks/issues/222) (Slack),
[#223](https://github.com/redact-secret/redact-secret-benchmarks/issues/223) (GitHub),
[#224](https://github.com/redact-secret/redact-secret-benchmarks/issues/224) (Stripe) and
[#225](https://github.com/redact-secret/redact-secret-benchmarks/issues/225) (Notion).
The product counterpart is redact-secret/redact-secret#729, which is blocked by #726.
This report records what the first run measured. It sets no support status and
makes no assertion about product output.

## What was authored

The contracts are in `benchmarks/lib/beta8/211.ts` and the corpus is
`fixtures/generated/beta8/211.mjs` (category `beta8-211`). Every value is a
`synthetic("beta8:211:…")` seed or code built from those seeds. None was
issued by a provider, copied from a provider example or derived from a real
credential.

Boundaries the fixtures keep:

- No twin changes a width. No twin introduces a character that a credible
  source admits (Stripe `+ / =`, GitHub `_`, Notion/lore `_ -`). Twins change
  only the prefix spelling, case or separator, add a glued leading letter, or
  insert one byte that no cited alphabet contains. The one exception is the
  Stripe public-prefix twin (`pk_live_`), which docs.stripe.com/keys documents
  as safe to expose.
- No fixture uses Nosey Parker's 42-character `xapp-` shape, the python-mock
  `xapp-` order without a version section, `development_ntn_`, `secret_`
  (the separate legacy Notion family), non-Stripe `whsec_` values (Svix /
  Standard Webhooks), or `ghs_`/`ghp_`/`xoxb-`/`xoxe-`/`nrt_` siblings. Those
  are all secrets, or shapes whose status is undecided, so none of them
  appears as a control or a twin.
- Controls are public or inert values only: token ids, request ids, the
  audit-log `hashed_token` digest, App/team/client ids, `we_`/`ed_test_`/`evt_`
  ids, `pk_test_` publishable keys, `Stripe-Signature` digests, Notion
  page/database/bot/workspace ids, placeholders, masks, references,
  prefix-only strings and prose.

### Product (redact-secret 0.1.0-beta.7)

The published product has no detector for these families. It already covers
every positive span exactly through its shared detectors. Scoring is by span,
not by which detector fired, so the table records each finding's product
family as an observation.

| Target | Positive spans exact | Product family on positives | Controls flagged | Twins with a product finding |
| --- | --- | --- | --- | --- |
| `github-fine-grained-pat` | 10 / 10 | `github-token` | 0 / 9 | 1 / 5: the case twin (`GITHUB_PAT_`) via `bearer-token` |
| `slack-app-level-token` | 10 / 10 | `slack-token` (interim `xapp-` guard) | 0 / 9 | 3 / 5: the boundary twin via `bearer-token`; the `_`-separator and digit-section twins via `slack-token` |
| `stripe-webhook-signing-secret` | 11 / 11 (10 fixtures, one with two rolling secrets) | `stripe-token` | 0 / 10 | 1 / 5: the boundary twin via `generic-token` (the `"secret":` key) |
| `notion-integration-token` | 10 / 10 | product label unmapped in `scanners/families.mjs` (`notion-token` is not in its redact-secret list) | 0 / 9 | 2 / 5: the separator twin via `bearer-token`; the alphabet twin via `generic-token` |

All product assertions passed: 0 failures across the metamorphic, mutation,
twin and benign methods. Twins are scoped to their arrival id. A product finding
attributed to a different, known family (`bearer-token`, `generic-token`,
`slack-token`) is therefore recorded as co-detection, not as a false alarm.
This has a consequence for these families. Because no product detector carries
an arrival id, no attributed product finding can fail an arrival twin, and
only an unattributed one could. The 5/5 twin discrimination per family should
be read with that in mind.

The two Slack twins that the product's `slack-token` detector flags are the
substantive case. The unpromoted interim guard (`xapp-[A-Za-z0-9_-]{20,}`)
accepts an `_` section separator and a letter in the all-digit third section.
No cited source admits either. These rows stay `open` for redact-secret#729
(class `differential-shared-detector-twin/slack-app-level-token`).

## Still open

- **Human-only corroboration**, from the #222–#225 hands-on checklists:
  - GitHub: the 93 total length, the `_` at offset 22, the `11` lead and a checksum.
  - Slack: section count, widths and alphabet, and whether section 2 is the App ID. Nosey Parker's contradicting rule is also unresolved.
  - Stripe: dashboard and CLI widths and alphabet, and whether `+ / =` ever occur.
  - Notion: the 11-digit run and its meaning, and whether PATs share the internal-integration grammar.
- **Open contract questions**, recorded but not decided here:
  - How non-Stripe `whsec_` values (Svix / Standard Webhooks) count.
  - Whether `development_ntn_` belongs to the Notion family.
  - A classification policy for arrival families, which decides whether the five Stripe classification rows can close.
- **Blockers:** none. Every family reaches `arrival-24`.
