## Input conversion

The four populations are never pooled: each is its own corpus snapshot, manifest, observation set, projection roster and artifact. A benchmark case that belongs to several views is a member of each view's population.

1. A case is carried located when the plan authors an identity (`valid` or `invalid`) and a target range. A case whose authored identity is `not-established` has no candidate range either; the oracle contract is closed over located valid and invalid cases, but schema 1.4 (pii-eval ADR 0017 and 0018) states it: identity `not-established`, sensitivity `not-established`, no range. It is carried range-less, counted below, never given an invented identity, and the engine reports it `unresolved`.
2. Every carried case is one `schema-only` case with its authored variant. The plans carry no frames, benign classes, collision targets or reference evidence, so no other method is invented; the three method-restricted metrics are not applicable here and are reported as such.
3. The frozen findings are the Beta.13 candidate's, with the pii-eval adapter policy applied (every PII finding is a sensitive classification with its family and jurisdiction). A finding equal to a declared line-sensitive span is not an observation of the case target, as in the benchmark's own scorer. A finding of another PII family is carried where the observation locates it at the target; an unlocated one cannot be placed.
4. The oracle's input is generated from the same case list and the same findings; the unmodified comparator regenerates the engine corpus from it and the result equals the replayed snapshot (text, ranges, families, expectations).

## Classified differences

| Id | Class | Layer / aspect | Count |
| --- | --- | --- | --- |
| `0007/D4` | compatibility | variant / operator | 3635 |
| `0007/D1` | compatibility | variant / variant-id | 3635 |

- `0007/D1` (compatibility): pii-eval variant ids are digests of case and slot; the oracle's variant id is the slot. The slot (`authored`) is compared equal.
- `0007/D4` (compatibility): an authored variant records no operator in the contract; the oracle records `authored`.
- No difference was an intentional contract change, an old bug or a new bug, and none is unresolved: the comparator found no difference of the canonical revision on these inputs (one authored variant per case; 0 carried case memberships have more than one finding after the line-sensitive rule). The oracle behaviors that revision 2 changes (`0004/D1` emission order, `0005/A2`, `0005/A3`, `0008/R3`, `0005/S1`) are classified by the same comparator on the upstream parity population, where they occur; they do not occur here.
- The 156 range-less memberships are not compared with the oracle (its contract is closed over located valid and invalid cases); each is checked against what the authors wrote (identity `not-established`, sensitivity `not-established`, no range, `schema-only`, neutral context) and against what the engine must report (`unresolved` on both outcome axes and the range, action `not-measured`). On the ten metrics their only effect is exact and stated: `total` and `notApplicable` grow by one each, and `measurable-share` counts each once per axis as `unresolved`, so its denominator grows by two each and its rate falls; every located numerator, eligible count, measured count, effective N and interval equals the oracle's. That is a change of the `measurable-share` denominator on the converted populations, recorded, not normalised; how a scorer reads it is the scorer-basis decision (#795).

## Limits

- Method coverage is `schema-only` only. The six other methods are exercised by the upstream parity population (37 cases, 54 variants), not by these populations.
- The benchmark scorer (`b11ScoreTable`) defines its metrics over its own sample sets (for example type misses among sensitive cases); `pii-v1` accounting defines them over valid-type occurrences. The two are different scorers, so their numbers are not compared here and neither replaces the other.
- A stored observation carries findings in canonical order, not scanner emission order (upstream ADR 0004 D2). The oracle received the frozen emission order; no carried case has two findings, so an emission-order dependence cannot occur on these inputs.
- The converted observation declares `reported-action`: the frozen observation recorded each finding's action but not a sanitized-output digest, so no output verdict is claimed.
- `b1c097e40bad` was built locally with `--locked`; the binary digest is platform specific and recorded only in the run output.

## Reproduce

```sh
git clone git@github.com:redact-secret/pii-eval.git "$PII_EVAL"    # any checkout that contains the pinned commit
node --import tsx scripts/run-pii-population-dual-run.mjs --pii-eval="$PII_EVAL" --check
npm run pii:migration:check
```

`--check` regenerates the inputs, the oracle exports, the replays and every comparison from the pinned sources and fails on any difference from the committed record and artifacts. It needs `git`, Node 22, and the Rust toolchain pinned by pii-eval.
