# Evidence adoption

How a published credential-evidence snapshot becomes the evidence this repository measures (#690). Decision:
[adopt evidence snapshots as a candidate, then an owner-accepted repin](../decisions/2026-10-03-adopt-evidence-snapshots-as-a-candidate-then-an-owner-accepted-repin.md).
This repository measures and records (the boundary rule): the workflow verifies, reports and prepares; it never asserts a product result and never accepts on the owner's behalf.

## States

`benchmarks/evidence-adoption.json` (gate: `npm run adoption:check`) records the one adoption in flight.

| State | Meaning | Active pins, runs and authority |
| --- | --- | --- |
| `none` | nothing in flight | unchanged |
| `candidate` | a verified, engine-readable snapshot with its change report; `ownerAcceptance` is `null` | **unchanged**: develop's `official-runs:check` and `authority:check` stay green and the old public numbers stay in force |
| `accepted` | the candidate is the active pin and carries the owner's acceptance (`acceptedBy`, `acceptedOn`, an existing ADR) | repinned, replayed, authority renewed by the owner |

The candidate state is the intermediate state: nothing a gate reads changes until the owner accepts. Only one candidate exists at a time; a second adoption stops with `conflict` until the first is accepted or withdrawn (delete the record: `{"schema": "redact-secret/evidence-adoption/v1", "state": "none"}`).

## Entry point

Dispatch `.github/workflows/adopt-evidence-snapshot.yml` with `tag` and `manifest_digest` (the digest `release:verify` in credential-evidence prints for the release manifest), plus, when the snapshot needs a newer engine than the registry's pin, `engine_tag` (for example `v0.1.0-alpha.4`), and `supersede: true` to replace a recorded candidate of another adoption. Or run the same command locally:

```bash
node scripts/adopt-evidence-snapshot.mjs prepare --tag snapshot-YYYY.MM.DD --manifest-digest sha256:<64 hex> \
  --engine-schema <credential-eval>/schemas/corpus-snapshot-v1.schema.json --out preflight-report.json --summary summary.md
```

`preflight` (the first half of `prepare`) changes nothing and ends with one of these outcomes and exit codes:

| Outcome | Exit | Meaning |
| --- | --- | --- |
| `ready` | 0 | identity verified and the pinned engine can read the snapshot |
| `already-pinned`, `already-prepared` | 0 | idempotent no-op (same tag and manifest digest as the pin, or same adoption key as the recorded candidate) |
| `identity-failed` | 3 | the manifest digest, the tag, the listed snapshot asset digest and size, the source/schema/records-tree identity or the case count disagree. **Not** an engine problem |
| `incompatible` | 4 | the pinned engine cannot read the snapshot: a report names each violated rule, how many cases and which semantic ids. No pin changes, no pull request |
| `conflict` | 5 | a different candidate is still recorded and `--supersede` (workflow input `supersede`) was not given |

**Engine compatibility.** The pinned engine refuses a snapshot that does not satisfy its closed corpus-snapshot v1 contract, so every case is validated against the engine's own schema at the pinned tag (the workflow fetches it with the existing read-only engine App token; `schemas/credential-eval-corpus-snapshot-v1.json` is the vendored copy used offline and the report says when they differ). A snapshot cannot be repaired here: its bytes are verified against the manifest, and a derived corpus would not be an official run. Expected-incompatible example: `snapshot-2026.10.03` against `v0.1.0-alpha.1` (75 of 504 added cases carry no `content`; #680). The decision is the owner's: an engine-readable evidence release or an engine change.

**A newer engine (`engine_tag`).** The compatibility check reads the snapshot with the engine that will replay it, not necessarily the active pin: with `--engine-tag`/`--engine-revision`/`--engine-run-schema` (the workflow resolves the tag to its commit and fetches both schemas with the engine token) the corpus-snapshot contract of that tag is the contract, the engine is part of the adoption key, and the record carries `engineChange` (from, to, the RunArtifact schema digest). The active registry, the vendored schemas and the authority are untouched; the engine pin moves only with the replay and the acceptance patch. Without it the active pin reads the snapshot, which is what `snapshot-2026.10.04.2` (needs engine >= alpha.4) failed on at the first dispatch (exit 4 against alpha.1; #690).

**Superseding a candidate (`supersede`).** A second adoption normally stops with `conflict`. With `--supersede` the recorded candidate is replaced: the new record holds `supersedesCandidate` (release, manifest digest, adoption key, engine, report and data paths), the superseded candidate's prepared acceptance patch and its digest file are removed (a patch that no longer matches the record must not be applied by mistake), its report and comparison data stay as history, and the change report carries `supersededCandidateDiff` (the case-level difference between the two releases and their representation facts). The owner accepts the new candidate and never the superseded one.

**Representation facts.** The change report carries `representation`: what the release declares (facts digest and counts from the manifest, cases by transformation operation, encoding codec, fragment mechanism, input validity and decoded codec). Those are the release's facts, not a measurement; whether the engine verified or scored them is the replay's finding (`replay.representationEffect`, `scripts/summarize-representation-effect.ts`).

**Idempotence.** The adoption key is the digest of the tag, manifest digest, snapshot digest and the engine, configuration and scanner pins. The branch is `adopt-evidence/<tag>-<first 12 hex of the key>`; the propose job skips when that branch or an open pull request exists. The workflow runs one at a time (`concurrency`, no cancellation). Releasing a snapshot stays manual; there is no schedule.

**Permissions.** Dispatch only. The preflight job has `contents: read` and the engine token (`contents: read` on credential-eval only). Only the propose job, after a passing preflight and only on `develop`, has `contents: write`, `pull-requests: write` and `actions: write`. GitHub starts no `pull_request` or `push` run for a commit or pull request made with the workflow token (observed on #727: the draft had no checks), but it does start a `workflow_dispatch` run, so after opening the draft the propose job dispatches `validate.yml` on the branch (it accepts a dispatch) and the required `validate` check reports on the draft's head commit; `actions: write` is only for that. If the dispatch is refused the pull request stays and the log tells the maintainer to push an empty commit. If the repository forbids Actions from creating pull requests, the branch is still pushed and the log says so. The `propose` job runs only on `develop`, so a dispatch from another ref runs the preflight and prepares the files without opening anything (how the entry point is tested before it is merged).

## The replay chain and the acceptance package as commands (#690)

What used to be hand work between the candidate pull request and the owner's decision is now five commands. Each is idempotent, refuses with the reason, writes data only, keeps `official-runs.yml` at `contents: read`, and never writes an owner field, the authority file or a deployment receipt of something not deployed.

| Command | Does | Writes |
| --- | --- | --- |
| `node scripts/run-evidence-replay.mjs branch\|dispatch\|wait\|collect --tag <tag> --manifest-digest <digest>` (`all` runs the four) | the control replay of the evidence candidate: a transient branch `replay/<tag>-<key12>-control` at the pushed HEAD plus the candidate's evidence pin (`repin`), one `official-runs.yml` dispatch (a run of the same commit that has not failed is reused, never dispatched twice), waiting, downloading, checking each run record (engine revision, replay commit, equal repeat digests, not a product candidate, the candidate's release), the archive release `official-runs-<run>` with a byte round trip, the record, and the deletion of the transient branch | `evidenceCandidate.replay` and `<tag>.replay-pins.patch` |
| `node scripts/run-evidence-replay.mjs chain --tag <tag> --manifest-digest <digest> --candidate <id>` | the control, then the product candidate on the accepted evidence and on the new evidence (`run-candidate-replay.mjs all --no-pr`, giving the 2x2), then the contrast, each step skipped when its record exists and committed and pushed before the next dispatch, then one draft pull request | the records of those steps and `<tag>.contrast.{json,md}` |
| `node scripts/run-evidence-replay.mjs contrast` / `scripts/render-snapshot-contrast.mjs` | the contrast of the new replays with the accepted ones by semantic id (`contrast-snapshots.ts --strict`): every difference is attributed to a case the change report names, anything else is unexplained and exits 1 | `<tag>.contrast.{json,md}` |
| `node scripts/prepare-acceptance-package.mjs --tag <tag> --manifest-digest <digest> --peers-dir <dir>` | on a transient worktree: `repin`, the four runs recorded, the registry-format archive stored in a release and fetched back, the derived inputs regenerated and proved by their `--check` commands, the candidate view, the legacy oracle with the pinned trufflehog (refused unless it prints the pin) and the strict parity report, the authority file and the accepted record with the owner fields `OWNER-TO-SET`, the draft decision (`status: proposed`); then in this checkout the owner report, its data, the triage queue (exported with the ledger as it was before the owner's settlement rows) and the re-evaluation of the ledger settlements on this run's identities | `<tag>.acceptance.patch` and `.sha256`, `<tag>.md`, `.comparison.json`, `.triage-queue.{json,md}`, `.ledger-settlements.json`, `evidenceCandidate.acceptance` |
| `node scripts/record-deployment-receipt.mjs --environment staging\|production --run <publish-site.yml run id> [--write]` | the deployment receipt of an ACCEPTED adoption, built only from what can be checked: the publish run (success, a push, on `develop` for staging and `main` for production, at a commit that holds the owner acceptance of this release) and the deployed pages (the evidence release, the engine, the scanned product and the maintainer-review disclosure in both languages must be on every listed page). A failed check writes nothing; a receipt is never typed in; a different receipt already recorded for the environment needs `--replace` | `candidate.deployment.<environment>` |

Still the owner's, by design: setting `acceptedBy`, `acceptedOn` and the decision, renewing the authority file, applying the patch, `go-production`, and the decision to apply a ledger settlement.

## What a candidate pull request holds

`benchmarks/evidence-adoption.json` and `docs/generated/evidence-adoption/<tag>.json`, keyed by stable semantic case ids: cases added, removed and changed (which of content, expected spans, grouping, twin, path), evidence-class transitions, added cases by kind, evidence class and group, new providers and families. Authored-base versus generated counts are the `group` split; where the evidence source does not mark generation, the report does not invent it. The scope line is fixed: corpus evidence only, scanner, engine and configuration pins unchanged, so the first replay changes evidence and nothing else. Product-version comparisons use the same corpus and configuration.

Review state, assertable versus unresolved expectations, and representation support come from the evidence release (the materialized manifest and records bundle), not from this repository. Draft is not non-assertable, and merged or released is not reviewed: use the release's recorded review state and the eligibility policy of the qualification inputs (`docs/specs/qualification-inputs.md`). A `T0` case is `measurement.type: pending`, outside TP/FN/FP and the denominators; a scanner that did not measure is `not-measured`. Neither becomes zero detections. A representation the engine cannot yet read (decoded, fragment, input validity) is reported as unsupported, never scored (credential-eval#34, credential-evidence#150).

## The prepared acceptance (#680)

After the replay, the candidate pull request also carries what the owner needs to decide and to apply, so the acceptance branch is a review of data and not a rebuild:

| File | What it is |
| --- | --- |
| `docs/generated/evidence-adoption/<tag>.md` and `.comparison.json` | The owner report and its data, written by `scripts/compare-adoption-views.ts` from three views built with `npm run qualification:view`: the accepted runs (A), the previous corpus replayed on the new engine with the review-ledger re-key regenerated (B), and the candidate (C). A to B is the engine effect, B to C the corpus effect with the overlays derived from it (axis overlay, twin-scope map, review-ledger re-key). Every status, matrix, gate and per-case difference is listed and attributed to the added cases (not common cases), the regrouping of common cases, or an overlay; a difference no rule attributes is listed under `unexplained` and `--strict` fails on one. |
| `docs/generated/evidence-adoption/<tag>.acceptance.patch` | The acceptance change as `git apply` data against the merged candidate: engine pin, the vendored RunArtifact schema, the run registry (the four canonical runs, the superseded runs as `historicalRuns[]`), the archive receipt, qualification inputs, the regenerated parity report, the three derived product overlays (axis overlay, twin-scope map, review-ledger re-key; single-line files, so they travel as binary deltas and `--check` regenerates them), the renewed authority file with the owner fields left as `OWNER-TO-SET`, the `accepted` record with the owner acceptance left as `OWNER-TO-SET`, and a draft ADR (`status: proposed`). It never fills an owner field: the gates stay red until the owner does. |
| `candidate.acceptance` in `benchmarks/evidence-adoption.json` | The patch path and digest, the digests of the three derived overlays as the patch leaves them (`npm run qualification:axis-overlay`, `qualification:twin-scope` and `qualification:ledger-rekey` with `--check` prove they are derived, not authored; the commands are in the record) and the digest and policy revision of the candidate view. `adoption:check` verifies the patch and the report exist and the patch digest matches. |

The owner applies the patch on an acceptance branch, optionally proves the overlays with the `--check` commands, sets the `OWNER-TO-SET` fields and the ADR status, and runs the gates. The active registry, schema and authority on `develop` do not change until then.

## Derived inputs and the view stage (#699)

The axis overlay, the twin-scope map and the review-ledger re-key are derived from one snapshot and bound to it by corpus digest; the committed copies under `benchmarks/support/` belong to the **accepted** population. A replay of a changed snapshot therefore never reads them and never overwrites them:

1. `node scripts/fetch-pinned-public-snapshot.mjs --out <dir>` downloads the registry's pinned snapshot and refuses unless the manifest digest, the listed asset digest and size, the release identity and the corpus digest are the pin's (on a replay branch the registry holds the candidate's pin, so this is the exact snapshot the replay measured).
2. `npm run qualification:derive-inputs -- --snapshot <file> --methods-run <methods/artifact.json> [--plain-run <artifact.json>] --out <dir>` derives the axis overlay and the twin-scope map from the snapshot and the re-key from the methods artifact that ran on it, and writes `derived-inputs.json`: the snapshot's corpus and bytes digests, the plain and methods artifacts' semantic digests, and a digest per generated file. An artifact of another corpus than the snapshot is refused, and so is an `--out` under `benchmarks/`. It prints, per file, whether it equals the committed copy; the committed copy is not read for the view.
3. `npm run qualification:view -- --artifacts <dir> --inputs <derived dir>` builds the candidate view from the derived directory only. All three files must be present, equal to the receipt, of the right identity and bound to the receipt's snapshot; the adapter still refuses an input bound to another corpus than the artifact (stale overlay, twin-scope map or re-key) with the command that regenerates it. Nothing was relaxed.

`official-runs.yml` does steps 1 to 3 in its view job and uploads the view with the receipt (`qualification-view` artifact: `qualification-v1.json`, `derived-inputs.json`). A dispatch with `reuse_run_id` (an earlier official-runs run of this repository) skips the scanner jobs and builds the view from that run's artifacts, so a failed view stage is retried without rerunning a scanner. Verified on the archived run 37202404479: the inputs derived from `snapshot-2026.10.04.3` and its methods artifact, and the view built from them, are byte-identical to the committed accepted ones.

The derived files reach `benchmarks/support/` only through the acceptance change (the patch carries them; `--check` of the three `qualification:*` commands proves they are derived). The receipt is the replay's record of what the view was built from.

## Report states (#700)

`scripts/compare-adoption-views.ts` renders the report against the record's current state (`scripts/adoption-report-state.mjs`): `candidate` asks the owner and says nothing is accepted; `accepted` shows the owner acceptance and its decision, labels the proposal instructions historical and the previous population the baseline, and lists what remains open. Deployment receipts are shown only when `candidate.deployment` holds them; an absent receipt is reported as absent (#680 collects them). The maintainer-only disclosure ("Maintainer-reviewed (independent review pending)" / "메인테이너 검토 (독립 검토 대기)") is in every state, and owner acceptance is never described as an independent review. Representation wording is the engine contract's: bounded, re-derivable base64 or hex findings (up to four layers) map to the whole original encoded segment; a fragmented expected span is scored on its enclosing range with no fragment-aware scoring; percent-encoded, UTF-16 and escaped-Unicode findings and unsupported mappings are unmeasured. The scanned product is stated as measured (alpha.4 measured beta.12); a beta.13 claim needs the pinned replay (#697). `--from-comparison` re-renders a recorded comparison without the views.

## Triage decisions (#698)

`scripts/apply-triage-decisions.ts` applies `benchmarks/qualification/triage-decisions.ts` to the exported queue: a classification and a disposition per root cause with the evidence it cites (a core issue or ADR, the verified replay, the evidence's own expected spans). The first matching rule decides; a root cause no rule decides stays open and is linked to a classification request. A peer divergence is justified only when the reference matches the case's expected result exactly (never by peer acceptance), a T0 pending case is not assertable, and a failure the product has not classified stays open. Ledger proposals are data, not ledger rows: no status moves. The maintainer-only disclosure rides on every output.

## Triage queue (#698)

`scripts/export-triage-queue.ts` (`npm run adoption:triage-queue`) exports `docs/generated/evidence-adoption/<tag>.triage-queue.json` (and `.md`) from the archived official artifacts (`node scripts/official-run-archive.mjs fetch --out <dir>`) and the pinned snapshot: core non-exact positives and flagged controls of the added cases, the unsettled gate-peer differential occurrences, and the reference scanner's failed metamorphic and mutation assertions on added cases. Each occurrence is keyed by case semantic id, method and operator, occurrence id (the engine's for a differential occurrence, a derived digest otherwise, marked) and the scanner, configuration and product identity; occurrences are deduplicated by root cause (seed case, kind, peer or method) with every affected occurrence kept. It is an export, not a decision: `classification`, `disposition` and `ledger` are `null`, nothing is settled and no status is restored. The final product attribution needs the pinned beta.13 replay (#697).

## Engine candidate on identical evidence (#697)

When the evidence release is already the accepted pin and only the engine or the product build changes (credential-eval alpha.4 measuring `@redact-secret/core` beta.12 became alpha.5 measuring beta.13), `adopt-evidence-snapshot.mjs prepare` with the accepted `--tag` and `--manifest-digest` plus `--engine-tag/--engine-revision/--engine-run-schema` and/or `--product-version/--product-integrity` records an `engineCandidate` next to the accepted adoption (never in place of it; `--supersede` replaces a recorded one; the key covers the engine, configuration and product pins). The gate (`adoption:check`) requires the identical evidence, a compatible engine, an existing change report and `ownerAcceptance: null`. The active registry, runs and authority stay as accepted until the owner decides.

The replay separates effects: the candidate run (new engine, new product) and an **attribution run** (new engine, the previous product build: `official-runs.yml` input `attribution`, the registry's `attributionRuns[<id>]`, always the engine's own configuration with its Node shim directory). A to B (accepted to attribution) is the engine and configuration effect, B to C (attribution to candidate) the product effect. `scripts/compare-replay-effects.ts` matches cases, assertions and review occurrences by semantic key, classifies every differing path as identity or outcome, lists the differing cases and reports any other path as unexplained (`--strict` fails on one). The pins ride on a transient replay branch (`runs: []`, the new engine and product, `attributionRuns`); the pins are kept as data (`docs/generated/evidence-adoption/engine-alpha.5/replay-pins.patch`), the branch is deleted after the artifacts are archived (a release per run), and the artifacts are archived as `official-runs-<run>` (candidate) and `attribution-runs-<run>` (attribution), never as accepted runs.

## Product candidate on identical evidence (#698)

An unpublished product build (a merged core fix that no release carries) is measured with the same engine candidate, evidence, populations, peers and methods as the control, as an exploratory, internal replay that is never an accepted run: [`product-candidate-replay.md`](product-candidate-replay.md). `scripts/run-candidate-replay.mjs all` does the steps that were by hand for the engine candidate (dispatch, wait, collect, archive with a round-trip check, report, receipt, draft pull request); `official-runs.yml` stays `contents: read`. The triage rules take the product's classification of the base cases from redact-secret#1203, and a proposed change to the evidence is an `evidenceProposal`, never applied here.

## Contrast with the previous snapshots, and owner-decided ledger settlements (#680, #698)

`node --import tsx scripts/contrast-snapshots.ts --from <older replay dir> --to <newer replay dir> --explain <explain.json> --strict` compares two replays of DIFFERENT snapshots by semantic id (cases, assertions, review occurrences): every difference must be attributed to a case the change reports name as changed (content, expected spans, grouping) or added, anything else is `unexplained`, and a worse outcome nothing explains is a regression; `--strict` exits 1 on either. `snapshot-2026.10.05` was contrasted with `.04.4` and `.04.3`, for the published control and the unpublished candidate: `docs/generated/evidence-adoption/snapshot-2026.10.05.contrast.md`.

A triage ledger proposal (`resolved` where the reference matches the evidence exactly and the divergence is the peer's, `not-assertable` for T0 pending) is data until the owner decides. `scripts/apply-ledger-settlements.ts` applies the owner-decided ones to `benchmarks/review-ledger.json` as rows keyed by the occurrence id of the ACCEPTED run (`sha256:<hex>`, the key `ledgerSettledId` reads first), and only where the same occurrence (case, peer, disagreement, variant, content digest, expected spans and findings) was proposed by the previous snapshot's triage and the accepted triage proposes the same settlement; everything else stays an unapplied proposal and reads unresolved. The receipt (`<tag>.ledger-settlements.json`) lists the applied and unapplied counts. The legacy rows are untouched; a settlement resting on a maintainer-only record says so in its note and none is an independent review. The parity report recognises the effect as the cause `owner-ledger-settlement` (the residual must equal exactly the rows).

## Known-gaps ledger currency (#680)

`benchmarks/known-gaps.json` carries a hand-set header (`reviewedAt`, `measuredVersion`, `milestone`) that nothing refreshes. After an acceptance the fixed and verified records are re-checked against the accepted run with `scripts/verify-known-gaps.ts` (read-only on the artifacts; a record whose fixtures are not in the run's corpora or whose fixture still fails keeps its status and is listed in the header's `reverification`; nothing is marked verified without evidence). `npm run known-gaps:currency:check` (in the validate workflow) fails when a record's newest history date is after `reviewedAt`, or `measuredVersion` is not the product release the accepted run scanned, so an acceptance of a new product release cannot leave the header behind. The pages say "ledger last reviewed / last measured release"; a finding's own label is the build it was recorded on (`candidate.version`), never the header's.

## From candidate to accepted

1. **Replay.** After the owner decides to proceed, open the acceptance branch from the candidate PR's branch and run `node scripts/adopt-evidence-snapshot.mjs repin --superseded-on YYYY-MM-DD`. It moves the floors population's pins in `official-runs.json` and `qualification-inputs.json` to the candidate and moves that population's existing runs (plain and methods) into `historicalRuns[]` as `status: "historical"` receipts with `supersededBy`. They are never relabelled as evidence of the new pin. `official-runs:check` accepts `historicalRuns[]` (a receipt that is really a run of the current pin is refused), and the authority check reads `runs[]` only.
2. Dispatch `official-runs.yml` on the exact reviewed commit (plain and methods drivers, pinned engine, scanners, configuration, linux-x64, two runs with equal semantic digests) and record the runs (`official-runs:record`, archive). Add outcome drift to the change report with `node scripts/adopt-evidence-snapshot.mjs compare-runs --report <report> --old <old artifact> --new <new artifact>`: common-case drift apart from added-case outcomes, and unmeasured counts.
   An engine bump rides on the same replay (#680: credential-eval `v0.1.0-alpha.3`, then #690: `v0.1.0-alpha.4`, which also needs the previous population and, to isolate the engine from a corpus revision, the superseded candidate's corpus replayed on it; each is one dispatch of `official-runs.yml` on a transient replay branch, a single run at a time because the workflow queues one pending run). It is a product-version effect, reported apart from the corpus change: replay the previous population on the new engine too (a transient branch with the previous pins and the new engine), then `node --import tsx scripts/summarize-adoption-replay.ts --report <report> --accepted <dir> --replay-old <dir> --replay-new <dir> --identity <json>` writes `replay.corpusEffect` (engine fixed), `replay.engineEffect` (corpus fixed), `replay.combined`, the unmeasured cases (RunArtifact v1.2 `unmeasured_cases`: in no denominator, never zero detections) and the data the owner needs to renew the authority. A methods artifact can exceed 700 MB, so `readRunArtifact` reads anything above 200 MB from its bytes (`large-json.ts`); the workflow uploads the run's artifacts even when the methods step fails. The replay commit is transient: the merged candidate keeps the active registry, the vendored schema and the old accepted runs, and the acceptance branch applies the engine pin, the schema, the config hashes and the recorded runs.
3. **Owner acceptance.** The owner renews the authority file in a reviewed commit (the gate `authority:check` is red on the acceptance branch until then, by design; the file is never rewritten automatically) and sets `state: accepted` with `ownerAcceptance` (an ADR). `adoption:check` refuses an acceptance without one.
4. **Staging.** Merge to `develop`; the push publishes `staging.benchmarks.redactsecret.dev`. Verify the stamps (evidence release, run digest) and that `develop` is green. Staging also needs the pii-eval App installation (#689).
5. **Production.** `npm run go-production` when the measurement is ready to be public. Record the staging and production receipts under `candidate.deployment`.
6. **Done** only when the record holds the snapshot tag, the manifest and snapshot digests, the run identities and digests, the deployment receipts and the disposition (accepted or withdrawn).
7. **Upstream acknowledgement.** Comment on credential-evidence#142 (the consumption issue) with the tag, digests, run ids and disposition.

## First real use (#690, snapshot-2026.10.04.3 on credential-eval alpha.4)

What the entry point did and did not do. The first dispatch (against the active alpha.1 pin) stopped with exit 4 (`incompatible`): the preflight read the snapshot with the registry's engine, not the engine that needs to replay it. Fixed here: `engine_tag` (resolved to a commit and to the engine's own schemas with the engine token), `supersede` (a second adoption used to stop with `conflict` with no way forward), the engine in the adoption key, `engineChange` and `supersedesCandidate` in the record, the superseded acceptance patch removed, representation facts and review state (`maintainer-only`, ADR 0020) in the change report. The preflight job was proven end to end from a branch (ready, supersedes the recorded candidate). The `propose` job runs only on `develop`, so opening the draft PR through the workflow could not be exercised before this change merged; this PR was opened by hand. Not automated and done by hand at that time: the transient replay branches and `official-runs.yml` dispatches, recording runs, the archive release, overlay regeneration, the three views, the comparison and the acceptance patch (commands since: [the replay chain and the acceptance package](#the-replay-chain-and-the-acceptance-package-as-commands-690)).
