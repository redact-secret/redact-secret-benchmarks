## Authority switch and rollback

The switch is explicit and reversible, and is one committed value, not a deletion.

- `benchmarks/qualification-authority.json` names the authority for credential qualification: `legacy` or `new` (the design called the second value `next`; it collides with the name of the web
  framework). Nothing infers it: no environment variable, no query string, no fallback to the other path. An absent file means `legacy`; a file that does not validate fails the build.
- Both pipelines keep running in CI while the setting exists, so the oracle stays current and the report can be regenerated.
- Flipping to `new` was one reviewed commit that also records the policy revision and the semantic digests of the canonical runs it is authorised for, the parity report and the ADR.
  Rolling back is a commit that sets the value to `legacy`; no data is migrated, so nothing has to be restored.
- The existing site's UI is not removed by an authority change. It is removed only when #543's UI migration criteria are met independently.

### The setting and its gate

```json
{ "schema": "redact-secret/qualification-authority/v1", "authority": "new",
  "legacy": { "role": "oracle", "oracle": { "exitCondition": "…", "decision": "docs/decisions/<adr>.md" } },
  "new": { "release": "@redact-secret/core@<version>", "acceptedOn": "<date>", "acceptedBy": "<owner>", "policyRevision": "rs-policy-1:sha256:<hex>",
           "semanticDigests": { "<population>": "sha256:<hex>", "<population>+methods": "sha256:<hex>" },
           "parityReport": "docs/generated/qualification-parity.json", "decision": "docs/decisions/<adr>.md" } }
```

`npm run authority:check` (in the `validate` workflow) holds three things. The file validates against `schemas/qualification-authority-v1.json` (and the same rules in `benchmarks/qualification/authority.ts`, which a
test keeps equal). While the value is `new`, the authorisation is still true: its policy revision is the one `loadPolicyRevision()` computes from the benchmark-owned inputs now, its semantic
digests are those of the canonical linux-x64 runs `benchmarks/official-runs.json` records (every one, none missing, none extra), the parity report it cites reports 0 unexplained and compared exactly those runs
and that policy, and the decision it cites exists and is accepted. A repin, a new official run or a policy change therefore makes `new` stale and the check fails until a reviewed commit authorises the new view.
While the value is `legacy` nothing is asked of `new`, and its block stays in place. Last, only the listed readers may name the file (`AUTHORITY_READERS`): a new reader is a decision, added there and
to the table below in the same change.

### Rollback path (criterion 7)

**What stays untouched, today and through the oracle period.** Everything the legacy path needs to produce its numbers and its site, so that
rolling back never depends on restoring anything: `benchmarks/run.ts`, `benchmarks/evaluate.ts`, `benchmarks/classify-support.ts`,
`benchmarks/generate-support-matrix.ts`, `benchmarks/engine/`, `benchmarks/evaluation/domains/credential/`, `benchmarks/lib/` (lattice, reporting,
peer observations), `benchmarks/review-ledger.json` and the committed peer observations, `src/` (the existing site) and its data model, the `web/`
services and pages that read the legacy files (`web/services/run.ts`, `catalog.ts`, `domains.ts`, `peers.ts`, `dossiers.ts` and `web/app/report/`), and the legacy
steps of the `validate` and `publish-site` workflows (`eval:classify`, `bench --strict`, `eval:publish`). The legacy outputs (`public/results/*`, `results-output/*`)
are generated, never committed, so they are rebuilt by the publish run and there is nothing to restore. The #606, #607 and switch work added files and changed none of the legacy computations: the legacy
`web/` services gained one seam in front of them (`credential-source.ts`) and a refactor that shares the catalog's indexing (`assembleCatalog`).

**How Next switches back.** Set `authority` to `legacy` in `benchmarks/qualification-authority.json` (or revert the commit that set `new`). The legacy pages never stopped reading the legacy files, so the revert
changes which pipeline the credential report pages are built from and what their stamps say. The qualification pages stay as the parallel set. No migration, no data restore, no re-run. `authority:check` then asks nothing of the
new path, and the authorisation block stays for the day it is flipped again.

**How the rollback is verified.** On the revert branch: `npm run eval:classify` and `npm run bench -- --strict` pass, `web` `npm run check` passes, and the staging site
(`develop` push) shows the legacy support status and matrix before `npm run go-production` is used. `web/scripts/with-authority.mjs <legacy|new> -- <command>` builds either value from one checkout without a
commit (it sets the value for the command and restores the file's bytes afterwards), and it is how the CI web job builds the legacy pipeline's export for the browser checks.

### How to read the inventory

- **Dispositions.** `keep` (the new path or a product-owned input uses it), `oracle` (kept while the legacy path is the oracle; removable at the oracle exit), `replace` (a replacement artifact must feed its consumers first, then it leaves),
  `move` (a shared type or validator lives in it and must be relocated before the file can go), `remove` (the legacy credential measurement, removable at the oracle exit once its callers are gone), `other-domain` (PII, protected holdout, blind, mixed-parity, performance: not part of #660).
- **Prerequisite codes.** **O** is the oracle exit above (an owner decision, not a code step): **met and recorded on 2026-10-05**, so a prerequisite of "O" is satisfied and what remains in such a row is the other code that follows it. **M** is "move the shared type or validator out first". **C2** to **C7** are #654 to #659; **V1** is credential-eval#33 (the compatibility retirement contract).
- **Callers** are the files outside the removal set that import the file (static import, `export … from`, dynamic import with a literal path) or name its repository path (package.json hooks, workflows, scripts, tests, tsconfig). They come from `node scripts/legacy-callers.mjs`,
  which is read-only. A path mention is counted as a caller, so a comment can over-count; a computed path would under-count, which is why the removal PR re-runs the script and reads the hits. `N test files` are counted, not listed; the script lists them.
- **The removal set** is every row marked `remove`; a caller inside it does not block, so "none" means nothing outside the set reads the file. A row with callers is not removable until each caller is migrated or itself removed.
- Anything not listed here is kept (see the end of this document). Removal never happens by directory: each removal PR names its files.

### C5 and C6 status (#657, #658)

- **Support matrix from the view (#657).** `npm run qualification:matrix` (`scripts/build-view-support-matrix.ts`, `benchmarks/qualification/matrix-artifact.ts`) writes the matrix from a validated view: shape-checked, bound to the pins of `benchmarks/official-runs.json`, with two modes that never mix.
  `published` accepts only public runs whose semantic digests the registry records as canonical and whose scanner manifests name no candidate build; `candidate-projection` is an explicit, allowlisted, internal staging projection (matrix entry fields only, never case rows, spans or observations) and can never be public. Wrong artifacts exit 1 and write nothing.
  It writes `results-output/support-matrix-from-view.json` beside, not over, the legacy `support-matrix.json`: the legacy file's validator demands legacy provenance (fixture-index identity, per-scanner observation provenance) that the view does not have, so `eval:publish:matrix`, the dossier roadmap and the domain index still read the legacy file. The comparison with the legacy matrix is the parity report's `matrix` section (attributed by rule, 0 unexplained); a plain equality check would erase the architecture difference.
- **Candidate diff and saved baseline from artifacts (#657).** `npm run qualification:candidate-diff` (`scripts/build-candidate-diff.ts`, `benchmarks/qualification/candidate-diff.ts`) reads the `candidate-run-*` artifacts of a product candidate replay and the control the adoption record binds by archive digest, and writes an internal, allowlisted projection (counts and measurement labels, no span or byte). It refuses a candidate artifact that is not exploratory and internal, is not the registered candidate at its exact tarball sha256 set (run record, receipt and, with `--verify-tarballs`, the registered bytes), does not hash to its record, or differs from the baseline in anything but the product build. Spec: [product candidate replay](product-candidate-replay.md#the-candidate-diff-and-the-saved-baseline-from-artifacts-657); decision: [read the candidate diff and baseline from artifacts](../decisions/2026-10-05-read-the-candidate-diff-and-baseline-from-artifacts-and-give-the-legacy-matrix-consumers-no-forged-provenance.md).
- **Legacy matrix consumers, decided.** They validate legacy provenance (`sourceReport`) the view cannot truthfully carry, so no compatibility envelope is written: they keep reading the legacy matrix until the oracle's exit condition, the view matrix serves new consumers, and a test fails if the legacy validator accepts a view matrix. `eval:candidate`, `web/services/candidate.ts` and the `publish-site.yml` legacy steps are unchanged (the service belongs to C6; the workflow is the oracle for the staging page). The candidate diff runs from the artifacts of a maintainer-dispatched replay; it is not a CI step because a push holds no candidate artifacts.
- **C6 (#658), what is done.** (1) Every import the Next app makes from `src/` and `benchmarks/` has a recorded role in `web/tests/unit/legacy-imports.test.ts`: a new import fails until it is listed, and a listed import that is gone fails too. (2) The shared validators and types moved to `benchmarks/shared/` (above); the Next app imports nothing from `src/` but the design tokens, and the Vite site keeps one-line shims. (3) Under authority `new`, `/comparison/`, `/comparison/accuracy/` and `/evaluation/scanner/` are built from the official run of the report population with the denominator named on the page and in its stamp, scanner identities from the artifact and no peer snapshot read; the owner's decision on denominators is [the ADR](../decisions/2026-10-05-read-comparison-and-scanner-pages-from-official-observations-with-separately-identified-denominators.md), and it is not an acceptance of any exit. (4) `check-export-comparison.mjs` recounts those pages from the view under `new`; the legacy recounts (`check-export.mjs`, `-rows`, `-accuracy`, `-scanners`) are intact and apply under `legacy`. (5) The catalog under `new` is the view's case metadata plus the taxonomy and detector-registry overlays (`credential-bridge.ts`); a test removes `fixture-index.json`, `fixture-detectors.json`, `scenarios.json` and `peer-observations/` from a root and the report, comparison, accuracy and scanner pages still build.
- **C6, what stays, and why.** The legacy catalog files and `web/services/catalog.ts`/`run.ts` remain: they are the `legacy` authority's pages and the rollback oracle, and the `/evaluation/` method pages still validate the legacy evaluation run against the corpus hashes. `benchmarks/fixture-index.json` and its generator are not replaced here because the legacy authority, `src/support-model.ts` and the matrix still read them (C8 owns that). `/comparison/runtime/`, `/comparison/feature/` and `/comparison/performance/` read PII and runtime evidence, never the credential run. The new-path recount of the fixture, family and report pages is `check-export-credential.mjs` (#654).
