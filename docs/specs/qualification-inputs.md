# Qualification inputs and corpus partitions

Issue: [#603](https://github.com/redact-secret/redact-secret-benchmarks/issues/603), part of epic
[#602](https://github.com/redact-secret/redact-secret-benchmarks/issues/602).
Decision: [Partition qualification inputs by population](https://github.com/redact-secret/redact-secret-benchmarks/blob/40809e8ce53eb94509d3b6bb3ae877ca8d4021f4/docs/decisions/2026-10-01-partition-qualification-inputs-by-population.md).

The machine contract is `benchmarks/qualification-inputs.json` (schema version 1), checked by
`npm run qualification-inputs:check` (`scripts/check-qualification-inputs.mjs`). The gate checks structure
only. It reads no fixture, count or ledger value, and this page and the manifest assert nothing about the
product: this repository measures and records.

## Why partitions

Credential qualification of Redact Secret reads more than one kind of evidence. Today
`loadCases()` (via `eval:classify`) reads the development and the regression partitions of
`benchmarks/categories.json` together and the support classifier reads one pooled result. After the split
the pool is not one corpus: credential-evidence is the public evidence population, not the only qualification
input. Each population below keeps its own owner, run class, pin and denominator. A number is always reported
with its population id. No report, adapter or page adds two populations' counts into one rate.

## Run classes

| Class | Meaning |
| --- | --- |
| `public` | A published-release run. Its aggregate results may be published. |
| `internal` | A candidate, unreleased or protected run. A product qualification artifact; never published as a public result. |

Run class is a property of the run, not of the evidence class. A population lists the classes it may be run in.

Notes that follow from the files:

- Population membership is by category and contract, not by assessment tier. The regression partition holds
  fixtures of kinds `must-redact`, `must-not-flag` and `policy`. The public snapshot holds T3 / project-policy
  fixtures as evidence class data. Neither is the policy corpus, which is the bounded behavior contract for the
  four named families (the Bearer, connection-string password, OTP seed and assignment-literal families).
- The candidate population is used "where needed": a family with no open finding has no row in it.
- Protected bytes never enter Git, credential-eval, a development job or a published artifact.
  PII, MCP, performance, shadow-scoring and other specialized domains stay outside this contract.
- No Redact Secret regression or policy fixture is copied into credential-evidence to keep qualification working.

## Pins per population

Every population entry records, in `pin`: source revision, corpus or snapshot digest, credential-eval
protocol and version where it applies, run artifact identity, and the Redact Secret product policy revision.
A pin field is a value or one of three states: `pending` (names the issue that resolves it), `resolved-at-run`
(names where the run records it) or `not-applicable` (names the reason). The public snapshot pin is fixed now:

| Field | Value |
| --- | --- |
| Evidence release | `snapshot-2026.10.01.2` of redact-secret/credential-evidence |
| Source revision | `a5362d6cfe644dcf069858ef9bd9cad4d7a96c4a` |
| Manifest digest | `sha256:2557a72ae8dec3ca6d734a6c87b6db9cb4881543541693a4555fdfd9f7ba26d8` |
| credential-eval snapshot digest | `sha256:1bc5a07b49dab7b8182f51bf11a65a9bb8a220adbd5216b364bc15b2d8e6a5af` |
| Engine | credential-eval `v0.1.0-alpha.4` (`57858c9`), protocol `credential-eval-protocol/1` |
| Legacy reference | `1020d2b5` |

`snapshot-2026.10.01` is superseded and the gate refuses it. The product policy revision is the revision of
the benchmarks-owned qualification inputs (`benchmarks/support/status-criteria.json`,
`policy-qualified-credentials.json`, `empirical-observations.json`) a run was qualified with. The adapter stamps it as
`rs-policy-<n>:sha256:<hex>` over those inputs and the others a status depends on
([qualification-adapter.md](qualification-adapter.md#product-policy-revision), #605). Each population's run artifact
identity is recorded in `benchmarks/official-runs.json` ([official-runs.md](official-runs.md), #604).

## Identity re-key

Canonical fixture ids, paths and identity digests in the evidence release differ from the legacy fixture index
by design, and credential-evidence does not translate digests. The switch re-keys stored per-fixture results,
peer observations and baselines once, using `credential-eval/legacy-id-map.json` from the pinned release, drops
any stored pin of the legacy fixture-index digest, and binds the public population to the evidence release tag
plus manifest digest. The manifest records this under `populations[0].rekey` (state `pending`, resolved with the
parity work in #607) so old-versus-new comparison runs on canonical ids.

## Evidence class and support status

Evidence class (provider-documented, tool-corroborated, project-policy, unresolved) and support status
(stable, provisional, pending) are separate axes. The snapshot supplies measured outcomes per fixture, each
carrying an evidence class. Qualification, owned here, supplies the route and the status:

1. The route (documented T1, empirical T2, policy-qualified T3) is read from the product-owned overlays above,
   never from the evidence class a snapshot fixture carries.
2. An empirically-qualified stable family whose public fixtures are now labelled project-policy keeps its
   empirical route. It continues to qualify while `empirical-observations.json` still meets its corroboration
   floor; the snapshot's evidence class is not a floor input. Its public fixtures count in the
   `public-evidence-snapshot` denominator with their new class and are not re-labelled.
3. The policy-qualified route stays limited to the four named families and still needs the policy corpus and a
   protected holdout on the same frozen candidate.
4. The public axis overlay is product policy, not evidence. It names the axis (source context of a positive, reviewed
   benign taxonomy of a control) a counted public case falls in, from the product's own authored fixtures, because the
   snapshot carries a scenario group and no benign taxonomy. It changes no evidence class, outcome or count, it is a
   component of the policy revision, and credential-evidence's evidence classes are untouched
   ([qualification-adapter.md](qualification-adapter.md#the-public-axis-overlay)).
5. A T2/T3 reclassification during migration, a per-fixture family override or a fixture moving between
   populations may not change a family's route or status by itself. A change needs an entry in
   `supportStatusChanges` with the family, an explicit product-policy reason, a decision record and the product
   policy revision; the gate refuses an entry without them. The list is empty.

## Denominator rules

1. One denominator per population, named by its id; the gate refuses a shared or combined denominator.
2. Counts from different populations are shown side by side with their ids and are never summed, averaged or
   merged into one rate, adapter row or page figure. The one thing taken across populations is the set of axis labels an axis floor
   reads (`population-policy.json` `axisCoverage`, #641): a union of names, with the supplying population shown per axis, never a count.
3. A fixture belongs to the population of the manifest that lists its category or contract. The two corpus
   manifests must not list the same category; the gate checks that.
4. A fixture in two families is counted once per family inside one population, as the family count decision
   states, and never across populations.
5. Internal-class runs (candidate, protected) are never mixed into a public result.
6. Protected cases contribute only an aggregate receipt; no row-level data leaves the custodian's workspace.
